# Диспетчерская: дизайн

2026-11-25. Первая подсистема Warehouse ([дорожная карта](../../roadmap.md)).

Пометки в тексте: **[владелец]** — решил владелец; **[предложение]** — решение автора документа;
владелец одобрил документ целиком 2026-11-25, не разбирая каждое по отдельности; всё остальное без пометки в разделе «Остаётся строителю» — на
усмотрение строителя.

## 1. Зачем

Владелец один ведёт 4–6 проектов (iOS-приложения Tenra, Dalada, Platina, библиотека DesignKit,
сайт Baja.kz). Код пишет Claude, почти всегда в облачных сессиях Claude Code; владелец работает
с телефона и десктопа и держит 5–8 сессий одновременно.

Что болит, словами владельца: «путаюсь в сессиях», «параллельные PR с разных сессий ждут своих
очередей, иногда это не видно и не понятно», «задержка растягивается на часы», «нет
прозрачности, теряется фокус, важные сообщения теряются в ленте потока сообщений от Claude».

Что за этим стоит (проверено по репозиториям и списку сессий 2026-11-25):

- Все четыре репозитория с приложениями собираются в GitHub Actions на раннере `xcode-27` и
  делят лимит одновременных сборок macOS одного аккаунта GitHub. CI Tenra идёт ~40 минут,
  скриншоты 70–180 минут. Сессия в одном проекте может стоять за сборкой другого и не знает об
  этом.
- Просьбы к владельцу («смержить вручную», «разблокировать телефон», «решить, чинить ли кейс»)
  лежат в последнем сообщении сессии. В списке сессий приложения Claude их не видно; некоторые
  висят неделями, часть — в уже заархивированных сессиях.
- Названия сессий не говорят, чей это проект («Tenra» ×3, «Продвижение застопорилось»). Связь
  сессия → ветка → PR → проект нигде не показана.

Диспетчерская — один экран и один канал уведомлений, которые отвечают на три вопроса:
**что ждёт меня**, **что сейчас с очередью сборок**, **что происходит в каждом проекте**.

## 2. Цели, не-цели, анти-цели

**Цели**

1. Список «Ждёт вас» по всем проектам: каждый пункт — одна строка с проектом, сутью, возрастом и
   ссылкой туда, где действовать (сессия или PR).
2. Общая очередь сборок macOS по всем репозиториям: что идёт, что ждёт, сколько осталось, чья это
   ветка и сессия, какие прогоны устарели.
3. По каждому проекту: активные сессии, открытые PR с состоянием CI и конфликтов, кто ведёт PR.
4. Сообщение в Telegram в момент, когда появляется новый пункт «Ждёт вас».
5. Данные обновляются сами: владелец ничего не вносит руками.

**Не-цели (эта версия)**

- Запуск и продолжение сессий со страницы (это «диспетчер с кнопкой», следующая версия).
- Мерж PR со страницы.
- Бэклог, планы, метрики, отзывы, идеи — другие подсистемы.
- Любые изменения в том, как сессии работают, кроме отчёта о состоянии (§5.2).
- Несколько пользователей.

**Анти-цели — так сервис провалится, даже если технически работает**

- Ещё одна шумная лента. Если «Ждёт вас» показывает то, что не требует владельца, или Telegram
  пишет чаще, чем нужно действие, владелец перестанет смотреть.
- Устаревшие данные без пометки. Экран, которому нельзя верить, хуже отсутствия экрана: у каждого
  блока видно время последнего обновления, а потеря источника (не приходят вебхуки, сессии не
  отчитываются) видна на странице.
- Утечка. Страница и её данные закрыты; секреты сервиса не попадают в репозитории (большинство
  репозиториев владельца публичные).
- Нагрузка на очередь macOS. Сервис не запускает сборок на macOS и сам на macOS не собирается.

## 3. Ограничения

- **Форма [владелец]:** веб-страница, удобная с телефона и с десктопа, плюс уведомления в
  Telegram. Нативное iOS-приложение не делаем (возможно позже, поверх тех же данных).
- **Список сессий Claude недоступен снаружи.** Документированного API, которым внешний сервер
  получит сессии пользователя и их состояние, нет (документация Claude Code, проверено
  2026-11-25). Изнутри сессии список читается инструментом `list_sessions` (id, название, статус,
  время, иногда краткое «что сделано / что нужно»). Плановые задачи Claude Code запускаются не
  чаще раза в час и могут пользоваться инструментами сессии.
- **Хуки** из `.claude/settings.json` репозитория срабатывают и в облачных сессиях (события
  `Stop`, `Notification`, `SessionEnd` и др.; у `SessionEnd` общий бюджет 1,5 с). Пользовательский
  `~/.claude/settings.json` в облаке не читается. Запрос из хука выходит через сетевую политику
  окружения: хост сервиса должен быть разрешён.
- **Секрет для хука** нельзя хранить в репозитории. В облачном окружении Claude Code есть
  «сетевые секреты»: значение хранится на окружении, а прокси сам подставляет заголовок в запросы
  к заданному хосту; сохранение такого секрета заодно разрешает хост. У владельца как минимум два
  окружения (Default и Tenra) — секрет нужен в каждом, где идут сессии проектов.
- **Очередь macOS общая на аккаунт**, а не на репозиторий; точный лимит одновременных задач для
  образа `xcode-27` (публичное превью) документом не зафиксирован — сервис выводит его из
  наблюдений (§5.4).
- **Репозитории:** Tenra, Dalada, Platina, DesignKit, Warehouse публичные; AutoParts4x4 (это
  проект Baja.kz) и CatPaw приватные. Все в одном аккаунте GitHub. Warehouse владелец может
  позже сделать приватным: сервис не должен от этого зависеть (никаких GitHub Pages, публичных
  ссылок на файлы репозитория, бесплатных только для публичных репозиториев возможностей).
- **Claude Ship** (агенты Steward/Approvals — только планы Team/Enterprise; `/ship` — только
  локальный CLI) сейчас владельцу в облаке недоступен. Дизайн от него не зависит, но поле «кто
  ведёт PR» (§5.3) оставляет для него место.
- Сервис живёт в репозитории `dkicekeeper/Warehouse`. Он публичный и остаётся публичным ради
  бесплатных минут GitHub Actions **[владелец, 2026-11-25]**; секретов в нём нет.

## 4. Подходы

Рассмотрены три.

**A. Без сервера: GitHub Action по расписанию + статическая страница (GitHub Pages).** Action раз
в 5–10 минут опрашивает GitHub, пишет JSON, шлёт в Telegram. Нет инфраструктуры. Но: задержка в
минуты (расписание Actions само опаздывает), страница публичная (а дальше на ней будут выручка и
метрики), нет места для отчётов сессий и для действий.

**B. Небольшой веб-сервис: Vercel + Supabase.** Вебхуки GitHub приходят на сервер, состояние в
базе, страница за входом, бот Telegram пишет сразу. Сессии отчитываются хуком; раз в час плановая
задача Claude сверяет список сессий. Остальные подсистемы дорожной карты ложатся в ту же базу.

**C. Страница, которую раз в час пересобирает плановая сессия Claude.** Кода почти нет, но данные
часовой давности, каждый прогон тратит токены, уведомления не в момент события. Для очереди, где
счёт на минуты, не годится.

**Выбран B [владелец].** Только он показывает очередь «сейчас» и сообщает «нужны вы» в момент
события; закрыт от посторонних; расширяется без переделки. Vercel и Supabase уже подключены к
сессиям Claude владельца, так что разворачивать и чинить сервис можно из сессий.

## 5. Как устроено

```
GitHub (все репозитории) ──вебхуки──▶ ┐
Сессии Claude ──хук Stop───────────▶ ├─▶ приём событий ─▶ база ─▶ страница (вход только владельцу)
Плановая задача Claude ──раз в час─▶ ┘                      └─▶ правила «Ждёт вас» ─▶ Telegram
```

### 5.1. Источник: GitHub

**[предложение]** Одно приложение GitHub (GitHub App), установленное на аккаунт владельца на все
нужные репозитории: один адрес вебхука на всё, работает с приватными репозиториями, права
точечные. Нужные события: `pull_request`, `pull_request_review`, `check_suite`/`check_run`,
`workflow_run`, `workflow_job`, `push`. Права: чтение метаданных, PR, проверок и Actions; запись в
Actions — только для отмены прогона (§5.5).

При первом запуске и при обнаружении пропуска (вебхук не дошёл) сервис досинхронизирует состояние
через API: открытые PR и прогоны за последние сутки. Периодическая сверка — на усмотрение
строителя, но расхождение не должно жить дольше ~15 минут.

Проект ↔ репозиторий: таблица соответствий в базе (проект может иметь несколько репозиториев:
Tenra и tenra-assets). Новый репозиторий, на который установлено приложение, появляется как
новый проект с именем репозитория; переименовать и объединить можно на странице настроек.

### 5.2. Источник: сессии Claude

Два канала, они дополняют друг друга.

**Отчёт сессии (в момент события).** В каждый репозиторий проектов добавляются:

1. Абзац в `CLAUDE.md`: в конце каждого хода, после которого Claude останавливается, последней
   строкой сообщения идёт строка состояния установленного вида, например
   `Статус: ждёт владельца — смержить PR #3` / `Статус: работаю — жду CI` /
   `Статус: готово — PR #3 смержен`. Три состояния: **ждёт владельца**, **работаю** (сессия
   остановилась, но вернётся сама: ждёт CI, события PR, таймера), **готово**. После тире — одна
   строка: что нужно от владельца или что сделано.
2. Хук `Stop` в `.claude/settings.json`: скрипт из репозитория читает последнее сообщение
   ассистента из транскрипта, достаёт строку состояния и отправляет сервису: id сессии,
   репозиторий, ветку, состояние, текст строки, время. Если строки состояния нет — отправляет
   состояние «неизвестно» и последние ~300 символов сообщения (чтобы пункт всё равно появился).
   Хук никогда не роняет и не задерживает сессию: короткий таймаут, ошибки глотаются.

Аутентификация хука: сетевой секрет окружения (§3) — токен подставляет прокси, в репозитории
его нет. Для локальных сессий на Mac владельца — переменная окружения. Запрос без верного токена
сервис отвергает.

Точный формат строки состояния, имена полей и способ достать последнее сообщение из транскрипта —
строителю (проверить по актуальной документации хуков, какие поля приходят в `Stop`).

Это первый элемент будущего «стандарта ведения проекта» (подсистема 2), и он идёт во все
репозитории сразу **[владелец согласился с этим следствием варианта B]**. Раскатка по
репозиториям — PR в каждый; порядок: Warehouse (на себе), затем Platina, DesignKit, Dalada,
AutoParts4x4 (Baja.kz), Tenra.

**Сверка раз в час.** Плановая задача Claude Code (новая сессия на каждый запуск) вызывает
`list_sessions`, для сессий, изменившихся с прошлого раза, берёт название, статус, время и краткое
резюме, и отправляет сервису тем же защищённым каналом. Она ловит то, что хук не видит: сессии в
репозиториях без хука, сессии вне репозиториев, архивирование, переименование, состояние «ждёт
разрешения/ввода». Плановая задача только читает и отправляет; ничего в сессиях не меняет.

**Связь сессия ↔ PR.** По ветке (хук присылает ветку; PR знает свою head-ветку) и по строке
`Claude-Session: https://claude.ai/code/session_…` в сообщениях коммитов PR. Если связать не
удалось, PR показывается с «сессия неизвестна» — это нормальное состояние, не ошибка.

**Проект сессии.** По репозиторию из отчёта хука; для сессий, известных только из сверки, — по
связанному PR, иначе «без проекта» с возможностью назначить вручную один раз (запоминается).

### 5.3. Экран

Одна страница, три блока сверху вниз; на телефоне — в один столбец в том же порядке.

```
ЖДЁТ ВАС (4)                                              обновлено 12 с назад
  Platina   PR #3 InfoTip — CI зелёный, смержить               9 ч    [PR] [сессия]
  Tenra     Прототип §14 — разблокировать телефон              7 дн   [сессия]
  Baja.kz   PR #13, #14 — решения по админке                  13 дн   [сессия]
  DesignKit Документация и gallery — посмотреть результат     30 мин  [сессия]

ОЧЕРЕДЬ macOS          идёт 2 · ждёт 3 · свободное место через ~55 мин
  ▶ Tenra    CI  claude/paywall-…   18 / ~40 мин    сессия «Tenra Маркетинг»
  ▶ Dalada   TestFlight 1.0.4       31 / ~50 мин    запущено вручную
  ⏳ Platina  CI  claude/infotip-…   ждёт 1 ч 10 мин сессия «InfoTip»
  ⏳ Tenra    CI  claude/paywall-…   устарел (есть новее)          [отменить]

ПРОЕКТЫ
  Tenra      3 сессии · 2 PR · 1 ждёт вас   ▸
  Dalada     1 сессия · 0 PR                ▸
```

- **Ждёт вас.** Сортировка: сначала новое непрочитанное, затем по возрасту. Пункт можно
  **закрыть** («сделал / не нужно») и **отложить** (до завтра, на неделю). Закрытый пункт
  возвращается, только если источник сообщил о нём заново с новым текстом.
- **Очередь macOS.** Задачи Actions, которые требуют macOS-раннера, со всех репозиториев.
  Идущие — с прошедшим временем и оценкой остатка; ждущие — со временем ожидания и оценкой начала.
  У каждой — репозиторий, workflow, ветка, сессия-владелец или «запущено вручную / по расписанию».
  Сборки на Linux в этот блок не попадают (они очередь не создают), но видны в проекте.
- **Проекты.** Раскрывается в: сессии (название, состояние, последняя строка состояния, возраст,
  ссылка), PR (номер, заголовок, CI, конфликт с базой, черновик, возраст, **кто ведёт**: сессия с
  действующим «работаю» / никто), последние прогоны. Сессия, которая подписалась на события PR
  и сама чинит CI и замечания, сообщает об этом строкой состояния («работаю — слежу за PR #3»):
  ни GitHub, ни хук сами этого не показывают. Третье значение (агент Claude Ship) появится, если
  владелец перейдёт на план с ним; сейчас не делаем.
- Ссылки на сессию открывают `https://claude.ai/code/session_…`, на PR и прогон — GitHub.
- Отдельная страница настроек: проекты ↔ репозитории, тихие часы Telegram, состояние источников
  (когда пришёл последний вебхук, последний отчёт хука, последняя сверка).

Визуальное оформление — строителю; ориентир — плотный, спокойный список, читаемый с телефона одной
рукой, светлая и тёмная темы. Макет показать владельцу до вёрстки всех состояний.

### 5.4. Правила «Ждёт вас» и оценки очереди

Пункт «Ждёт вас» создаётся, когда:

| Источник | Условие | Текст |
|---|---|---|
| Отчёт сессии | состояние «ждёт владельца» | строка состояния сессии |
| Отчёт сессии | состояние «неизвестно» | хвост последнего сообщения, пометка «без статуса» |
| Сверка | сессия ждёт ввода/разрешения или у неё непрочитанный результат, а отчёта хука о ней нет | резюме из списка сессий |
| GitHub | PR не черновик, все проверки зелёные, конфликтов нет, по нему нет действующего «работаю» | «готов к мержу» |
| GitHub | проверки PR упали, и по нему нет действующего «работаю» | «CI упал, никто не чинит» |
| GitHub | упала сборка на `main` | «main красный» |

Не создаётся пункт: сессия «работаю» или «готово»; PR-черновик; PR, по которому сессия уже
сообщила «ждёт владельца» (один пункт на одну причину — склеивать по сессии и PR).
Пункт закрывается сам, когда причина исчезла (PR смержен или закрыт, сессия прислала новое
состояние, CI позеленел).

**Срок действия «работаю» [предложение].** Состояние «работаю» само по себе не вечно: сессия
могла сказать «жду CI» и не вернуться — это и есть исходная боль. «Работаю» действует 2 часа с
момента отчёта и продлевается, пока для ветки сессии есть прогон в очереди или идущий. Когда срок
вышел, сессия для обоих правил GitHub считается не работающей, а сама попадает в «Ждёт вас» с
текстом «сессия молчит: <последняя строка состояния>». Срок — в настройках.

**Два уровня пунктов [предложение].** *Просьба* — владельца явно позвали или что-то сломано:
отчёт «ждёт владельца», «main красный», «CI упал, никто не чинит», «готов к мержу». *Заметка* —
сервис догадался сам: «без статуса», пункты из сверки, «сессия молчит». На странице видны оба
уровня (заметки ниже просьб и бледнее). В Telegram сразу уходят только просьбы; заметки —
одним сообщением раз в день, утром, и только если они есть.

Оценки очереди:

- Длительность прогона — медиана последних успешных прогонов того же workflow в том же
  репозитории; пока истории нет — без оценки («~?»).
- Лимит одновременных задач macOS — наибольшее число одновременно идущих, которое сервис наблюдал
  при непустой очереди; можно задать вручную в настройках.
- «Устарел» — прогон в очереди или идущий, для чьей ветки и workflow уже есть прогон на более
  новом коммите.
- Все оценки показываются с «~»; это подсказка, а не обещание.

### 5.5. Действия

Страница в этой версии почти только показывает. Действия: закрыть и отложить пункт; **отменить
прогон** в очереди macOS (кнопка у устаревших и у любых ждущих, с подтверждением) —
**[предложение]**: отмена лишней сборки напрямую сокращает очередь, вред от ошибки мал (прогон
перезапускается). Мерж, перезапуск, запуск сессий — не в этой версии.

### 5.6. Telegram

Бот пишет в личный чат владельца. Сообщение уходит, когда появляется новый пункт «Ждёт вас»;
в нём — проект, суть, ссылки на сессию/PR и на страницу. Правила против шума:

- сразу уходят только пункты уровня «просьба» (§5.4); заметки — одним сообщением утром;
- одно сообщение на пункт; изменение текста того же пункта редактирует сообщение, а не шлёт новое;
- пункты «готов к мержу» и «CI упал» уходят с задержкой в несколько минут: если причина исчезла,
  сообщение не отправляется;
- тихие часы (по умолчанию ночь по Алматы): накопленное приходит одним сообщением утром;
- закрытие пункта на странице ничего не шлёт.

Очередь сборок в Telegram сама не пишет. Привязка чата к боту и формат сообщений — строителю.

### 5.7. Доступ и секреты

- Вход на страницу — только владелец **[предложение: вход через GitHub, один разрешённый аккаунт]**.
  Без входа не отдаётся ничего, включая API чтения.
- Вебхуки GitHub проверяются по подписи; отчёты сессий и сверки — по токену.
- Все секреты (ключ приложения GitHub, токен бота, токен приёма отчётов, ключи базы) — в
  переменных окружения Vercel и сетевых секретах окружений Claude. В репозитории — только имена.
- В базе не хранится содержимое сессий, кроме строки состояния и короткого резюме.

### 5.8. Стек — решения автора, не владельца

> **Изменено 2026-11-26 [владелец]:** Supabase не используется — на бесплатном плане у владельца
> заняты оба проекта. База — Postgres в Neon, вход — напрямую через приложение GitHub (подписанная
> cookie), тик — GitHub Actions раз в 5 минут вместо минутного. Абзац ниже — первоначальный
> вариант; актуальное описание — в `ops/setup.md`.

**[предложение]** Next.js на Vercel, Postgres и вход в Supabase, TypeScript. Причина: оба сервиса
подключены к сессиям Claude владельца (деплой, логи, миграции из сессии); сборка и тесты идут на
Linux и очередь macOS не трогают. Конкретные библиотеки, схема таблиц, способ живого обновления
страницы (подписка на изменения базы или опрос раз в 10–20 с) — строителю.

## 6. Что считается готовым

1. Владелец открывает страницу с телефона, входит, видит три блока с реальными данными по Tenra,
   Dalada, Platina, DesignKit, Baja.kz.
2. Сессия в репозитории с хуком завершает ход строкой «ждёт владельца» → пункт на странице и
   сообщение в Telegram в пределах минуты.
3. Пуш в рабочую ветку, запускающий сборку macOS, появляется в очереди в пределах минуты с верной
   привязкой к ветке и, если известна, к сессии; после завершения — исчезает.
4. Устаревший прогон помечен, кнопка «отменить» его отменяет.
5. Смерженный PR убирает свой пункт «готов к мержу» без участия владельца.
6. Отключение источника (например, отозванный вебхук) видно на странице настроек и пометкой на
   главной не позже чем через час.
7. Неавторизованный запрос к странице, к API и к приёму событий ничего не раскрывает.
8. Автотесты покрывают правила §5.4 (создание, склейка, автозакрытие пунктов; «устарел»; оценки) —
   это логика, на ошибках которой сервис превращается в шум.

## 7. Остаётся строителю

Схема базы; структура кода; формат строки состояния и полезной нагрузки хука; скрипт хука и его
поведение при недоступном сервисе; как плановая задача определяет «изменилось с прошлого раза»;
живое обновление страницы; вёрстка и оформление; формат сообщений Telegram; способ привязки чата;
стратегия досинхронизации с GitHub; хранить ли сырые события и как долго; локальная разработка и
тесты; порядок миграций.
