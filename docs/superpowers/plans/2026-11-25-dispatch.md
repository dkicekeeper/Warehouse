# Диспетчерская Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Закрытая веб-страница и бот Telegram, которые по всем проектам владельца показывают «Ждёт вас», общую очередь сборок macOS и связь проект ↔ сессии Claude ↔ PR.

**Architecture:** Приложение Next.js на Vercel принимает вебхуки GitHub, отчёты хука сессий и часовую сверку, складывает состояние в Postgres (Supabase). Вся логика — чистые функции в `lib/domain/` (правила «Ждёт вас», сверка пунктов, оценки очереди, план уведомлений); один оркестратор `recompute()` вызывается после каждого события и раз в минуту по тику из `pg_cron`. Страница читает готовое состояние опросом раз в 15 с.

**Tech Stack:** Next.js (App Router, последняя стабильная на момент создания) · TypeScript strict · Vitest · Supabase (Postgres, Auth с провайдером GitHub, `pg_cron` + `pg_net`) · `octokit` + `@octokit/webhooks` · Zod · Tailwind · Telegram Bot API через `fetch` · pnpm · Node 22.

**Spec:** [docs/superpowers/specs/2026-11-25-dispatch-design.md](../specs/2026-11-25-dispatch-design.md) — исполнитель читает оба документа; план ссылается на параграфы спецификации как «§N».

## Global Constraints

- Никаких секретов в репозитории (он публичный и остаётся публичным — решение владельца): только имена переменных в `.env.example`.
- Сборка и тесты идут только на `ubuntu-latest`; ни одного задания на macOS.
- Без входа владельца не отдаётся ничего: ни страницы, ни `/api/board`, ни действия. Открыты только `/login`, `/auth/callback` и четыре приёмника (`/api/github/webhook`, `/api/report/*`, `/api/telegram/webhook`, `/api/cron/tick`), каждый со своей проверкой подписи или токена.
- К базе ходит только сервер ключом service role; RLS включён на всех таблицах без политик.
- В базе из сессий хранится только разобранное состояние, строка состояния и не более 300 символов хвоста сообщения.
- Проекты первой версии: Warehouse, Tenra (+ tenra-assets), Dalada, Platina, DesignKit, Baja.kz (`dkicekeeper/AutoParts4x4`).
- Значения по умолчанию: срок «работаю» 120 мин; задержка уведомления для `pr_ready` и `ci_failed` 5 мин; тихие часы 23:00–08:00 `Asia/Almaty`; опрос страницы 15 с; сырые события хранятся 14 дней.
- Тексты интерфейса и сообщений — на русском. Идентификаторы в коде — на английском.
- Хук никогда не роняет и не задерживает сессию: общий таймаут 5 с, код выхода всегда 0, ничего в stdout.
- Все оценки времени в интерфейсе — со знаком «~»; неизвестное — «~?».

## Review Focus

1. **Повторные и перепутанные по порядку вебхуки** (GitHub повторяет доставку; `completed` может прийти раньше `in_progress`): состояние прогона и PR не откатывается назад, дубликат ничего не меняет. → Task 8.
2. **Строка состояния в «неидеальном» виде**: в `**жирном**` или обратных кавычках, с дефисом вместо тире, с пустыми строками после, на английском, с эмодзи перед словом «Статус». Должна разбираться; при неудаче — `unknown`, а не исключение. → Task 2.
3. **Сервис недоступен, медленный или хост закрыт сетевой политикой**, когда срабатывает хук: сессия этого не замечает (выход 0 за ≤5 с, пустой stdout). → Task 12.
4. **Telegram отказал** (бот заблокирован, 429, таймаут): пункт не помечается отправленным, следующая минута повторяет; успешная отправка с упавшей записью в базу не даёт второго сообщения больше одного раза. → Task 10.
5. **PR и ветки с историей**: force-push, удалённая ветка, закрытый и заново открытый PR, PR без единой проверки, `mergeable: null`. Пункты закрываются сами; единственный прогон ветки не помечается устаревшим; PR без проверок не «готов к мержу». → Task 3 и Task 5.

- Produces (`status-line.ts`): `parseStatusLine(message: string): ParsedStatus`

Формат строки состояния (решение плана; §5.2 оставляет его строителю): последняя непустая строка сообщения вида `Статус: <состояние> — <текст>`. Состояния: `ждёт владельца` → `needs_owner`, `работаю` → `working`, `готово` → `done`; английские синонимы `needs owner` / `needs-owner`, `working`, `done` и ключ `Status:`. Разделитель — `—`, `–` или ` - `. Перед разбором со строки снимаются обрамляющие `*`, `_`, `` ` ``, `>` и ведущие не-буквенные символы (эмодзи). Регистр не важен. Не разобралось → `{ state: 'unknown', text: <последние 300 символов сообщения, обрезанные по пробелам> }`.

Правила (§5.4), в порядке применения:

| Вид | Уровень | key | Условие | text |
|---|---|---|---|---|
| `session_needs_owner` | request | `session:<id>` | не в архиве, `state === 'needs_owner'` | `stateText` |
| `session_unknown` | note | `session:<id>` | не в архиве, `state === 'unknown'`, есть `reportedAt` | `без статуса: <stateText>` |
| `session_silent` | note | `session:<id>` | `state === 'working'` и `!isWorking(...)` | `сессия молчит: <stateText>` |
| `session_reconcile` | note | `session:<id>` | нет `reportedAt` или `reconcile.updatedAt > reportedAt`; `bucket` — `blocked` или `failed`, либо `review_ready` и `unread` | `reconcile.summary ?? title ?? 'ждёт ответа'` |
| `pr_ready` | request | `pr:<repo>#<n>` | open, не draft, `checks === 'success'`, `mergeable === true`, нет работающей сессии по PR | `PR #<n> <title> — готов к мержу` |
| `ci_failed` | request | `pr:<repo>#<n>` | open, не draft, `checks === 'failure'`, нет работающей сессии по PR | `PR #<n> <title> — CI упал, никто не чинит` |
| `main_red` | request | `main:<repo>:<workflow>` | последний завершённый прогон workflow на `defaultBranch` с `conclusion === 'failure'` | `main красный: <workflow>` |

- `isWorking`: `state === 'working'`, не в архиве, и (`now - reportedAt ≤ workingTtlMin` **или** есть прогон `queued`/`in_progress` с `repo === s.repo && branch === s.branch`).
- «Сессия по PR» — `pr.sessionId === s.id` или совпадают `repo` и `branch`.
- Склейка: если по PR есть пункт `session:*` его сессии (любого вида), пункты `pr:*` этого PR не создаются.
- Архивная сессия не даёт пунктов, кроме `session_reconcile` с `bucket === 'blocked'` (в спецификации §1 отмечено: просьбы остаются в архивных сессиях).
- `since`: для сессии — `reportedAt ?? reconcile.updatedAt`; для PR — `updatedAt`; для `main_red` — `completedAt` прогона.
- `projectId` — сессии, иначе репозитория.

- История для оценки — завершённые успешные задания с тем же `repo` и `name`; меньше одного → `null`.
- Лимит `L = cfg.macosLimit ?? cfg.observedMacosLimit`. `observeLimit`: если есть хотя бы одно ждущее mac-задание, вернуть `max(prev ?? 0, число идущих mac-заданий)`, иначе `prev`.

- `freeSlotInMin` — когда началось бы ещё одно, гипотетическое задание; `0`, если место есть сейчас.
- `origin`: по `run.event` — `workflow_dispatch` → `manual`, `schedule` → `schedule`; иначе `session`, если нашлась сессия с тем же `repo` и `branch`, иначе `push`.
- Строки: сначала идущие (по убыванию `elapsedMin`), затем ждущие (по `createdAt`).
