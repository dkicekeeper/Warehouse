# Стандарт ведения проекта: дизайн

2026-11-26. Подсистема 2 [дорожной карты](../../roadmap.md). Одобрен владельцем 2026-11-26.

## Зачем

У владельца шесть репозиториев (Warehouse, Tenra, Dalada, Platina, DesignKit, Baja.kz), код и
документы в них пишет Claude в 5–8 параллельных облачных сессиях. Сейчас в каждом своя система
документов: в Tenra плоский `docs/` с `backlog.md` прозой и `plan-*.md`; в Dalada нумерованные
папки и вехи `M1–M34`; в Platina один `PLAN.md`; в DesignKit бэклог размазан по `CLAUDE.md`,
`benchmark.md` и `adoption.md`; в Baja.kz три старых плана. Статус везде записан текстом.
Определений «можно брать» и «сделано» нет.

Следствия: информация теряется, сессия в новом проекте не знает, где что лежит, а следующим
подсистемам Warehouse (панель бэклога, автономный менеджер) нечего читать одинаково.

## Цели

1. Одно дерево `docs/` во всех репозиториях, текущих и будущих.
2. Задачи, планы, решения и паспорт проекта несут статус **полями**, которые читает машина.
3. Определены «готово к работе» (DoR) и «сделано» (DoD), чеклисты начала работы, завершения,
   выпуска и нового проекта.
4. Правила для сессий лежат в одном месте (Warehouse) и сами попадают в `CLAUDE.md` каждого
   репозитория.
5. Соблюдение проверяет CI, а не память сессии.
6. Все шесть репозиториев переведены на стандарт; ничего из открытой работы при переезде не
   потеряно.

## Не цели

- Показывать бэклог и планы на панели Warehouse: это подсистема 3. Здесь только формат, который
  она будет читать.
- Автоматически выбирать и запускать задачи: подсистема 5.
- Переводить документы на другой язык. Tenra и DesignKit остаются на английском, остальные на
  русском.
- Менять содержание предметных документов (архитектура, домены, гайды). Они только переезжают.

## Чего нельзя допустить

- Потеря открытой задачи, решения владельца или действующего правила при переезде.
- Битые ссылки внутри `docs/` и из `CLAUDE.md`.
- Сломанные инструменты, которые читают документы по путям (ниже, «Пути, которые нельзя трогать»).
- Формат, который заставляет параллельные сессии править один файл.

## Ограничения

- Репозитории публичные (кроме Baja.kz): в документах нет секретов и личных данных.
- Все проверки стандарта идут на `ubuntu-latest`; ни одного задания на macOS.
- Переезд репозитория идёт одним PR и сталкивается с ветками работающих сессий, поэтому
  репозитории переводятся по одному, когда в нём мало открытых PR.

## Подходы

Глубина (выбор владельца 2026-11-26):

1. Тонкий слой: одинаковый набор файлов поверх существующих документов. Дёшево, но пять систем
   остаются.
2. **Полная унификация: все репозитории на одно дерево.** Выбрано: «в Dalada и Platina не так
   много всего».
3. Стандарт только для новых проектов. Панель бэклога для нынешних не построить.

Хранение задач (выбор владельца 2026-11-26):

1. **Файл на задачу с полями в шапке.** Выбрано: параллельные сессии не правят один файл.
2. Один `backlog.md` со строгим форматом. Читается глазами, но конфликты при мерже неизбежны.
3. GitHub Issues. Задачи уходят из md и от кода.

## Дерево

```
CLAUDE.md                 правила проекта + блок стандарта (между метками, пишет workflow)
AGENTS.md                 только если его требует инструмент
docs/
├── README.md             оглавление: строка на каждый файл docs/ (кроме backlog, plans,
│                         decisions, archive)
├── project.md            паспорт проекта (поля + короткое описание)
├── backlog/              открытые задачи, файл на задачу
├── plans/                дизайн-документы и планы в работе, файл на план
├── decisions/            решения владельца, которые действуют, файл на решение
├── domains/              по файлу на предметную область
├── public/               сайт GitHub Pages, если есть
├── archive/              всё, что перестало быть актуальным
│   ├── backlog/          сделанные и отменённые задачи
│   ├── plans/            выполненные и отменённые планы
│   └── decisions/        отменённые решения
└── <имя>.md              остальные актуальные документы, плоско: architecture.md,
                          release.md, growth.md, testflight.md, gotchas.md, …
```

Правила дерева (взяты из `docs/README.md` Tenra, где они уже работают):

- В `docs/` только актуальное: то, что описывает проект как он есть, и работа в ходу.
  Неактуальное уезжает в `docs/archive/` тем же коммитом, который сделал его неактуальным.
- Папок ровно семь, перечисленных выше; новых не заводят. Исключение: каталоги, которые читает
  инструмент (ниже).
- Имена: строчные латинские буквы, слова через дефис, даты ISO. Исключения: `README.md`, коды
  локалей.
- В актуальных документах нет истории («раньше было так»): она в сообщении коммита и в архиве.
- Навыки, которые по умолчанию пишут в другие места (superpowers в `docs/superpowers/`), пишут
  и дизайн, и план в `docs/plans/`.

### Пути, которые нельзя трогать

Их читают скрипты и workflow. Переезд их не переименовывает:

- DesignKit: `CHANGELOG.md`, `.changes/`, `docs/components.md`, `docs/components.json`,
  `docs/agents.md`, `docs/localization-keys.md`, `docs/migration-*.md`, `docs/design-system.md`
  (на них ссылаются приложения и release bot).
- Tenra: `docs/public/` (сайт, `scripts/build_site.py`), `docs/release-notes.md`, и всё, что
  называют по имени плановые задачи Claude (их тексты хранятся вне git, проверено 2026-11-26):
  `docs/promotion-plan.md`, `docs/plan-growth.md`, `docs/asc.md`, `docs/threads.md`,
  `docs/domains/*.md`. Субботняя задача называет ещё `docs/backlog.md`: он становится папкой,
  поэтому текст этой задачи правится в день мержа переезда Tenra (шаг плана, с согласия
  владельца).
- Dalada, Platina: `docs/public/`.
- Ссылки между репозиториями (DesignKit называет `docs/PLAN.md` Platina, приложения называют
  документы DesignKit): проверка их не видит. При переезде репозитория поиск его старых путей
  идёт по всем шести, правки в чужих репозиториях — отдельными маленькими PR.
- Любой путь, найденный поиском по `.github/`, `scripts/` и коду перед переездом репозитория:
  либо остаётся, либо меняется вместе со ссылкой в том же PR.

## Форматы

Шапка — YAML между строками `---` в начале файла. Ключи и значения-перечисления английские.
Проверка принимает только описанные ключи.

### Задача: `docs/backlog/<id>.md`

`id` равен имени файла без `.md`: `<дата создания>-<слово-или-два>`, например
`2026-11-26-assistant-attachments`. Счётчика нет: параллельные сессии не могут столкнуться
номерами.

```
---
status: ready            # idea | ready | in-progress | blocked | done | dropped
type: feature            # feature | bug | chore | research | content | growth
priority: 2              # 1 срочно, 2 обычно, 3 когда-нибудь
size: m                  # s до часа сессии, m одна сессия, l нужен план
created: 2026-11-26
updated: 2026-11-26
needs-owner: "выбрать цену"   # нет ключа — владелец не нужен
plan: plans/2026-11-20-notifications.md   # нет ключа — плана нет
branch: claude/…         # ставит сессия, когда берёт задачу
pr: 142                  # номер PR, когда открыт
---
# Вложения ассистента после перезапуска

Зачем: одно-два предложения, какую боль это снимает.

Готово, когда:
- проверяемое условие;
- ещё одно.

Заметки: что уже известно, ссылки.
```

Заголовок первого уровня обязателен. Разделы «Зачем» и «Готово, когда» обязательны со статуса
`ready` (у `idea` достаточно заголовка и абзаца).

Жизнь задачи: `idea` → `ready` → `in-progress` → `done`; в любой момент `blocked` (тогда
`needs-owner` или строка «Ждёт: …» в заметках обязательны) и `dropped`. Файл со статусом
`done` или `dropped` лежит только в `docs/archive/backlog/`; переносит его тот же PR, который
закрыл задачу.

`in-progress` и `branch` сессия пишет в своей рабочей ветке, не в `main`: в `main` задача
остаётся `ready` до мержа. Кто чем занят, панель (подсистема 3) узнаёт из открытых веток и PR,
которые меняют файл задачи. Две сессии на одной задаче возможны, но сейчас сессии запускает сам
владелец; замок на задачу появится вместе с автономным менеджером (подсистема 5), в базе
Warehouse.

### План: `docs/plans/<дата>-<тема>.md`

```
---
status: approved         # draft | approved | in-progress | done | dropped
kind: design             # design | plan
created: 2026-11-26
updated: 2026-11-26
approved: 2026-11-26     # дата одобрения владельцем; обязателен со статуса approved
tasks: [2026-11-26-assistant-attachments]   # id задач, которые план закрывает; можно пусто
---
```

`done` и `dropped` живут только в `docs/archive/plans/`.

### Решение: `docs/decisions/<дата>-<тема>.md`

```
---
status: active           # active | superseded
decided: 2026-10-14
by: owner                # owner | claude (решение сессии, которое владелец не отменял)
supersedes: 2026-09-01-pricing   # нет ключа — ничего не заменяет
---
# Цели накоплений бесплатны

Решение: одно-два предложения.
Почему: причина.
```

`superseded` живёт только в `docs/archive/decisions/`.

### Паспорт: `docs/project.md`

```
---
name: Tenra
stage: live              # idea | development | beta | live | maintenance
kind: ios-app            # ios-app | web | library | service
platforms: [ios]
standard: 1              # версия стандарта, по которой устроен репозиторий
links:
  store: https://…
  site: https://…
  testflight: true
---
# Tenra

Что это и для кого: абзац.
Сейчас: одна-две строки о том, чем проект занят (версия в сторе, ближайшая веха).
```

## Определения

**Готово к работе (DoR)** — условия статуса `ready`:

1. Есть «Зачем» и «Готово, когда» с проверяемыми условиями.
2. Нет открытого вопроса к владельцу (`needs-owner` отсутствует).
3. Стоят `type`, `priority`, `size`.
4. У задачи размера `l` есть одобренный план (`plan`, его статус `approved` или дальше).

Сессия не берёт в работу задачу, которая не `ready`: сначала доводит её до `ready` или
спрашивает владельца.

**Сделано (DoD)** — условия статуса `done`:

1. Все условия «Готово, когда» выполнены и проверены, а не предположены.
2. CI репозитория зелёный на ветке.
3. Документы, которые изменение сделало устаревшими, обновлены тем же PR.
4. Изменение, которое видит пользователь, записано в заметки к выпуску проекта, если они есть.
5. Файл задачи перенесён в `docs/archive/backlog/` со статусом `done` и номером PR; план,
   у которого закрыты все задачи, — в `docs/archive/plans/`.
6. Новое, что всплыло по ходу и не сделано, записано задачами в `docs/backlog/`.

## Чеклисты

Все четыре — части блока стандарта в `CLAUDE.md`.

- **Начало работы.** Прочитать `docs/project.md`; найти задачу в `docs/backlog/` или создать
  её; проверить DoR; поставить `in-progress` и `branch`.
- **Завершение.** DoD по пунктам; строка состояния (уже действует, переезжает в блок).
- **Выпуск** (приложения): версия поднята; заметки к выпуску на всех языках проекта; сборка в
  TestFlight из зелёного `main`; шаги владельца перечислены в строке состояния. Подробности
  проекта остаются в его `docs/release.md`.
- **Новый проект.** Скопировать шаблон дерева; заполнить `project.md`; первая задача в бэклоге;
  подключить workflow стандарта; добавить хук отчёта сессии.

## Где живёт стандарт и как попадает в проекты

В Warehouse появляется каталог `standard/`:

```
standard/
├── VERSION               целое число; растёт, когда меняется формат или дерево
├── agents.md             блок правил для CLAUDE.md: дерево, форматы, DoR, DoD, чеклисты,
│                         строка состояния (нынешний раздел «Строка состояния для Warehouse»
│                         переезжает сюда)
├── template/             дерево нового проекта: docs/README.md, project.md, пустые папки
│                         с .gitkeep, пример задачи
├── lint.py               проверка репозитория на соответствие (Python 3, без зависимостей)
├── sync_block.py         пишет agents.md в CLAUDE.md между метками
│                         <!-- warehouse:standard:start --> и <!-- warehouse:standard:end -->
└── workflow.yml          образец .github/workflows/standard.yml для проектов
```

В каждом репозитории `.github/workflows/standard.yml` на `ubuntu-latest`:

- **на PR и пуш:** забирает `standard/` из `main` Warehouse и запускает `lint.py`. Красный, если
  дерево или поля нарушены;
- **раз в сутки и вручную:** запускает `sync_block.py`; если блок изменился, коммитит его в
  `main` от `github-actions[bot]` (как workflow DesignKit update в приложениях).

Блок правил написан на русском во всех репозиториях (как уже стоящий раздел о строке состояния).

### Что проверяет `lint.py`

Архив — история. В `docs/archive/` разрешены любые подпапки и имена; файл без шапки там не
проверяется вовсе (102 старых плана Tenra, вехи `M1–M34` Dalada переезжают и остаются как есть).
Файл архива с шапкой проверяется по правилам 3, 4 и 6.

1. В `docs/` нет папок, кроме разрешённых, и исключений из списка «нельзя трогать» данного
   репозитория (список исключений — файл `docs/.standard.json` в самом репозитории: пути,
   которые проверка пропускает, с причиной).
2. Есть `docs/README.md` и `docs/project.md`; шапка паспорта полная.
3. Каждый файл в `backlog/`, `plans/`, `decisions/` и их архивах имеет шапку только из
   описанных ключей с допустимыми значениями; имя начинается с ISO-даты.
4. Статус соответствует месту: `done`/`dropped`/`superseded` только в архиве, остальные только
   вне его.
5. Правила DoR: у `ready` и дальше есть разделы «Зачем» и «Готово, когда» (в английских
   репозиториях «Why» и «Done when»); у `blocked` есть причина; у `l` со статусом
   `in-progress` есть `plan`, и файл плана существует.
6. Ссылки `plan`, `tasks`, `supersedes` ведут на существующие файлы (в том числе в архиве).
7. Относительные ссылки markdown в `docs/**` (кроме `archive/`) и в `CLAUDE.md` ведут на
   существующие файлы.
8. Имена файлов в `docs/` (кроме исключений) — строчные через дефис.
9. Каждый плоский файл `docs/*.md` и `docs/domains/*.md` упомянут в `docs/README.md`.

Вывод — по строке на нарушение: путь, что не так, как исправить. Код выхода 1 при нарушениях.
`lint.py --json` печатает разобранные задачи, планы, решения и паспорт: этим же разбором
подсистема 3 будет читать репозитории.

## Переезд репозиториев

Порядок: **Warehouse → Baja.kz → Platina → Dalada → DesignKit → Tenra**. Сначала свой
репозиторий (на нём отлаживается проверка), потом от малого к большому. Каждый переезд — один PR
в репозитории, мерж владельца; перед началом мержатся или закрываются открытые PR этого
репозитория, насколько возможно.

Общий порядок в каждом репозитории:

1. Найти все пути документов, которые читают `.github/`, `scripts/` и код.
2. Перенести файлы `git mv`, чтобы история сохранилась.
3. Разобрать открытую работу на задачи, планы и решения (правила ниже).
4. Исправить ссылки; переписать раздел о документах в `CLAUDE.md` проекта под стандарт.
5. Добавить `standard.yml`, блок стандарта, `docs/.standard.json`.
6. `lint.py` зелёный; CI репозитория зелёный.
7. В описании PR — таблица «было → стало» и счёт: сколько задач, планов, решений создано и из
   каких разделов.

Правила разбора:

- Открытый пункт бэклога или невыполненный пункт плана → задача. Статус `ready`, если из текста
  ясно «зачем» и «готово, когда»; иначе `idea`. Пункт, который ждёт владельца, → `blocked` с
  `needs-owner`.
- Идеи «не сейчас» → задачи `idea`, `priority: 3`.
- Решения владельца («решение владельца от …», разделы Decisions) → файлы решений.
- Выполненные планы и вехи → `archive/plans/` целиком, без разбора на задачи.
- Текст источника сохраняется: задача несёт абзац источника дословно, а не пересказ.
- Источник правды один. Раздел, разобранный на задачи и решения, из исходного файла удаляется
  (на его месте строка-ссылка на папку). Решения извлекаются только из документов бэклога и
  планов (Decisions в `backlog.md` Tenra, §8 и §10 `PLAN.md` Platina). Правила, записанные в
  `CLAUDE.md` проектов, остаются там как есть: сессия читает их при старте.
- Бессрочные документы с названием «план» (стратегия роста, продвижение: `plan-growth.md`,
  `plan-sales.md`, `promotion-plan.md` Tenra, `promotion.md` Dalada) — не планы стандарта, а
  обычные плоские документы; имена не меняются. В `docs/plans/` идёт только работа с концом.

По репозиториям:

| Репозиторий | Что переезжает |

## Проверка

- `lint.py` и `sync_block.py` покрыты тестами в Warehouse: набор маленьких деревьев-образцов
  (правильное и по одному на каждое нарушение), тесты запускают скрипт так же, как уже
  проверяется хук отчёта.
- `standard/template/` само проходит `lint.py` (тест).
- После каждого переезда: `lint.py` зелёный в CI репозитория; счёт задач в описании PR
  сходится с числом открытых пунктов источника.
- Приёмка: в каждом из шести репозиториев `lint.py --json` отдаёт паспорт, задачи, планы и
  решения; блок стандарта в `CLAUDE.md` совпадает с `standard/agents.md`.

## Что решил я (владелец может поправить)

- Образец дерева — Tenra.
- `id` задачи из даты и слова, без счётчика.
- Решения — отдельные файлы, а не раздел бэклога.
- Блок правил на русском во всех репозиториях; документы остаются на своём языке.
- Проверка — Python без зависимостей, берётся из `main` Warehouse при каждом запуске (версия
  не закрепляется; несовместимое изменение стандарта Warehouse выкатывает вместе с правкой
  репозиториев).
- Warehouse переезжает первым.
- Дизайн-документы и планы лежат вместе в `docs/plans/`, различаются полем `kind`.
