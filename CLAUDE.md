# Warehouse

Сервис владельца для ведения всех его проектов. Работает первая подсистема — **диспетчерская**:
закрытая страница и бот Telegram, которые показывают «Ждёт вас», общую очередь сборок macOS и
связь проект ↔ сессии Claude ↔ PR. Вторая — **стандарт ведения проекта**: каталог `standard/`
(правила, проверка, шаблон), по которому устроены все репозитории владельца.

- Паспорт и оглавление документов: [docs/project.md](docs/project.md), [docs/README.md](docs/README.md)
- Дорожная карта: [docs/roadmap.md](docs/roadmap.md)
- Развёртывание: [docs/setup.md](docs/setup.md)
- Диспетчерская, спецификация и план (выполнены):
  [дизайн](docs/archive/plans/2026-11-25-dispatch-design.md), [план](docs/archive/plans/2026-11-25-dispatch.md)
- Next.js здесь новее, чем в обучающих данных: правила в [AGENTS.md](AGENTS.md), документация в
  `node_modules/next/dist/docs/`.

## Команды

```bash
pnpm install
pnpm test        # vitest, база внутри процесса
pnpm test:pg     # те же тесты через боевой драйвер на настоящем Postgres (TEST_DATABASE_URL)
pnpm test:e2e    # сборка + браузерные тесты
pnpm typecheck
pnpm lint
pnpm build
```

## Правила

- Никаких секретов в репозитории (он публичный): только имена переменных в `.env.example`.
- Сборка и тесты только на `ubuntu-latest`; ни одного задания на macOS.
- Без входа владельца не отдаётся ничего. Данные отдают только `/api/board`, `/api/backlog`,
  `/api/settings`, `/api/guides`, `/api/metrics` и действия, каждый после проверки cookie. Открыты только `/login`, `/auth/*` и приёмники
  (`/api/github/webhook`, `/api/report/*`, `/api/telegram/webhook`, `/api/cron/tick`), каждый со
  своей проверкой подписи или токена.
- К базе (Postgres в Neon) ходит только сервер по `DATABASE_URL`. Supabase не используется.
- Схема базы — миграции в коде (`lib/store/migrations.ts`); сервис применяет их сам при тике.
  Вышедшую миграцию не правят, изменения идут новой.
- Метрики (`lib/metrics/`, расчёты в `lib/domain/metrics.ts`): тик раз в сутки забирает RevenueCat,
  продажи App Store и Apple Ads по ключам из Vercel (`docs/setup.md`, «Метрики»). Цифры о деньгах —
  только за входом владельца; в ответе тика и в ошибках источников — статусы и коды, без чисел и
  тел ответов.
- Тесты хранилища идут на Postgres внутри процесса (PGlite) и, в CI, на настоящем Postgres через
  боевой драйвер: они по-разному кодируют параметры.
- Вход — через то же приложение GitHub: подписанная cookie `wh_session` на 30 дней, проверяется в
  каждом обработчике `/api` рядом с данными; `proxy.ts` только отсекает запросы без cookie.
- Часы сервиса — три источника сразу, потому что ни один не надёжен в одиночку: расписание
  GitHub Actions раз в 5 минут (`tick.yml`; стартует с задержкой и пропускает запуски), «пульс» —
  тик не чаще раза в минуту после любого вебхука, отчёта сессии и запроса открытой панели
  (`tickIfDue`), и cron Vercel дважды в сутки (`vercel.json`) ради утренней сводки.
  В лог `tick.yml` нельзя печатать ответ сервиса — логи публичные.
- Из сессий в базе хранится только разобранное состояние, строка состояния и не более 300
  символов хвоста сообщения.
- Панель бэклога читает `docs/` репозиториев сама (`GithubApp.syncDocs`): пуш в основную ветку
  помечает репозиторий, тик читает помеченные, раз в 30 минут все. Разбор шапки в
  `lib/domain/docs.ts` обязан совпадать с `standard/lint.py` (тест сравнивает их на одних файлах);
  меняется формат — меняются оба.
- Гайдлайны — `standard/guides/`: общие правила всех проектов с номерами (формат в их
  `README.md`), сайт показывает их в разделе «Гайдлайны» (`/api/guides`, разбор
  `lib/domain/guides.ts`). Блок `standard/agents.md` собирает из разделов «Коротко для агента»
  `standard/build_agents.py`; тест падает, если блок устарел. Правило меняется PR; номера не
  перенумеровывают. Аудит по ним — `standard/guides/audit.md`.
- `standard/` читают все репозитории владельца из `main` (workflow `standard.yml` в каждом):
  изменение формата или дерева поднимает `standard/VERSION` и выкатывается вместе с правкой
  репозиториев. Скрипты там — Python без зависимостей; тесты в `tests/standard/`.
- Вся логика — чистые функции в `lib/domain/`, покрытые тестами; сначала падающий тест, потом код.
- Интерфейс — на [shadcn/ui](https://ui.shadcn.com/) (`components.json`, стиль `base-nova`): компоненты
  добавляет её CLI (`pnpm dlx shadcn@latest add <имя>`) в `components/ui/`, руками их не пишут.
  Страницы владельца лежат в `app/(app)/` внутри рамки `components/shell.tsx` и читают доску из одной
  копии (`components/board-data.tsx`, опрос `/api/board`); собираются из `components/page.tsx`; цвета только токенами темы (`bg-card`,
  `text-muted-foreground`, `text-destructive`, свои `text-success` и `text-warning`), тёмная тема —
  по системной настройке.
- Тексты интерфейса и сообщений — на русском, идентификаторы в коде — на английском.
- Оценки времени в интерфейсе — со знаком «~»; неизвестное — «~?».

## Стандарт ведения проекта

Один порядок во всех проектах владельца. Правила целиком, с причинами и способами проверки, — в
[гайдлайнах](https://github.com/dkicekeeper/Warehouse/tree/main/standard/guides) репозитория Warehouse (их же показывает сайт Warehouse, раздел «Гайдлайны»);
номер в скобках, например (DOC-2), — номер правила там. Документы проверяет CI (workflow
`standard.yml`); локально: `python3 -I <Warehouse>/standard/lint.py --root .`

### Проекты

- Работай в ветке `claude/…`; в `main` — только через PR с зелёным CI. Прямо в `main` пишут
  только владелец и боты своих workflow (PRJ-3).

### Документы

#### Где что лежит

```
docs/
├── README.md      оглавление: строка на каждый документ docs/ и docs/domains/
├── project.md     паспорт проекта
├── backlog/       открытые задачи, файл на задачу
├── plans/         дизайн-документы и планы в работе (и навыков superpowers тоже)
├── decisions/     действующие решения владельца, файл на решение
├── domains/       по файлу на предметную область
├── public/        сайт GitHub Pages
├── archive/       всё неактуальное: backlog/, plans/, decisions/ и остальная история
└── <имя>.md       остальные актуальные документы, плоско
```

- В `docs/` только актуальное: проект как он есть и работа в ходу. Неактуальное уезжает в
  `docs/archive/` тем же коммитом, который сделал его неактуальным (DOC-2).
- Новых папок в `docs/` не заводят. Путь, который читает инструмент, вносится в
  `docs/.standard.json` (`{"ignore": [{"path": "…", "reason": "…"}]}`) (DOC-3).
- Имена: строчные латинские буквы и цифры, слова через дефис, даты ISO. Исключения:
  `README.md`, коды локалей (DOC-4).
- В актуальных документах нет истории («раньше было так»): она в сообщении коммита и в архиве
  (DOC-5).
- Новый документ получает строку в `docs/README.md`. Ссылки внутри `docs/` и из `CLAUDE.md`
  должны вести на существующие файлы (DOC-6, DOC-7).
- Бессрочные документы (стратегия, продвижение) лежат плоско; в `docs/plans/` только работа
  с концом.

#### Форматы

Шапка: YAML между строками `---` в начале файла. Только эти ключи и значения (DOC-8).

**Задача** `docs/backlog/<ГГГГ-ММ-ДД>-<слово>.md` (имя файла и есть её id; счётчика нет):

```
---
status: ready        # idea | ready | in-progress | blocked | done | dropped
type: feature        # feature | bug | chore | research | content | growth
priority: 2          # 1 срочно, 2 обычно, 3 когда-нибудь
size: m              # s до часа, m одна сессия, l нужен план
created: 2026-11-26
updated: 2026-11-26
---
# Название задачи

Зачем: какую боль это снимает.

Готово, когда:
- проверяемое условие.

Заметки: что известно, ссылки.
```

Ещё четыре ключа, когда они нужны: `needs-owner: "что нужно от владельца"` (такая задача
`blocked`, не `ready`), `plan: plans/<файл>.md` (путь от `docs/`), `branch: claude/…` (ставит
сессия, которая взяла задачу), `pr: 142` (когда PR открыт). Списки пишутся в одну строку в
скобках. В репозиториях с английскими документами разделы называются `Why`, `Done when`,
`Notes`. У `idea` достаточно заголовка и абзаца; `priority` и `size` обязательны с `ready`.

**План** `docs/plans/<ГГГГ-ММ-ДД>-<тема>.md`: `status` (draft | approved | in-progress | done |
dropped), `kind` (design | plan), `created`, `updated`, `approved` (дата одобрения владельцем,
обязательна с `approved`), `tasks: [id, id]`.

**Решение** `docs/decisions/<ГГГГ-ММ-ДД>-<тема>.md`: `status` (active | superseded), `decided`,
`by` (owner | claude), `supersedes: <id>`; в тексте строки «Решение: …» и «Почему: …».

**Паспорт** `docs/project.md`: `name`, `stage` (idea | development | beta | live | maintenance),
`kind` (ios-app | web | library | service), `platforms: [ios]`, `standard: 1`, `links:` с
вложенными `store`, `site`, `testflight`; ниже — что это, для кого и чем проект занят сейчас.

Закрытое живёт только в архиве: задача `done` или `dropped` — в `docs/archive/backlog/`, план
`done` или `dropped` — в `docs/archive/plans/`, решение `superseded` — в
`docs/archive/decisions/`. Переносит файл (`git mv`) тот же PR, который его закрыл (DOC-9).

#### Готово к работе (DoR, DOC-10)

Задача `ready`, когда:

1. Есть «Зачем» и «Готово, когда» с проверяемыми условиями.
2. Нет открытого вопроса к владельцу (иначе она `blocked` с `needs-owner`).
3. Стоят `type`, `priority`, `size`.
4. У задачи размера `l` есть одобренный план (`plan`, статус плана `approved` или дальше).

Задачу, которая не `ready`, в работу не берут: сначала доведи её до `ready` или спроси владельца.

#### Сделано (DoD, DOC-11)

Задача `done`, когда:

1. Все условия «Готово, когда» выполнены и проверены, а не предположены.
2. CI репозитория зелёный на ветке.
3. Документы, которые изменение сделало устаревшими, обновлены тем же PR.
4. Изменение, которое видит пользователь, записано в заметки к выпуску проекта, если они есть.
5. Файл задачи перенесён в `docs/archive/backlog/` со статусом `done` и номером PR; план, у
   которого закрыты все задачи, — в `docs/archive/plans/`.
6. Новое, что всплыло по ходу и не сделано, записано задачами в `docs/backlog/`.

#### Чеклисты

**Начало работы.** Прочитай `docs/project.md`. Найди задачу в `docs/backlog/` или создай её.
Проверь DoR. В своей рабочей ветке поставь `status: in-progress`, `branch` и обнови `updated`.

**Завершение.** Пройди DoD по пунктам. Закончи сообщение строкой состояния (ниже).

**Новый проект.** Скопируй `standard/template/` из Warehouse. Заполни `docs/project.md`. Запиши
первую задачу. Добавь `.github/workflows/standard.yml` (копия `standard/workflow.yml`) и хук
отчёта сессии (`hooks/` в Warehouse).

### Сессии Claude

#### Строка состояния для Warehouse

Каждое сообщение, после которого ты останавливаешься, заканчивай отдельной последней строкой
(SES-1):

`Статус: <состояние> — <одна строка>`

- `ждёт владельца` — без владельца дальше нельзя: что именно от него нужно (решение, мерж, проверка на устройстве, секрет).
- `работаю` — ты остановился, но вернёшься сам: чего ждёшь (CI, событие PR, таймер). Если следишь за PR и чинишь его — `работаю — слежу за PR #N` (SES-3).
- `готово` — работа закончена и от владельца ничего не нужно: что сделано.

Строку читает сервис Warehouse и показывает владельцу; без неё сессия попадает в список «без статуса».

### Сборки и CI

- Код, который не собирается в контейнере, проверяет CI: запушил — прочитай логи прогона (CI-1).
- Раннеры macOS общие на все приложения: не запускай их зря, лишняя сборка задерживает чужую
  (CI-2).

### Секреты

- Репозиторий публичный вместе с историей и логами Actions: что туда попало, опубликовано (SEC-1).
- Секретов в репозитории нет: только имена переменных; попавший в коммит ключ отзывают (SEC-2).
- Workflow не печатает в лог токены, ответы сервисов и личные данные (SEC-3).
- Ключ API для облачной сессии — сетевой секрет окружения, не переменная и не чат (SEC-4).

### Выпуск приложений

**Выпуск** (приложения). Версия поднята (REL-2). Заметки к выпуску на всех языках проекта
(REL-3). Сборка в TestFlight из зелёного `main` (REL-1). Шаги владельца перечислены в строке
состояния (REL-4). Подробности проекта — в его `docs/release.md`.

### Дизайн-системы

- Интерфейс приложений — только из DesignKit; чего нет — PR в DesignKit, в приложении тонкий
  переходник (DES-1). Только токены, без сырых значений (DES-2). Версию DesignKit поднимает его
  workflow, блок `designkit:agents` руками не правят (DES-3, DES-4).
- Сайты — на shadcn/ui, цвета только токенами темы (DES-7).
- Каждая строка интерфейса приложения — ключ каталога строк на всех языках проекта (DES-8).

### Аудит

- Нашёл, что проект отступил от правила гайдлайнов, — запиши задачу в `docs/backlog/` со ссылкой
  на номер правила; правило устарело — предложение задачей в Warehouse, правило не меняй
  (`standard/guides/audit.md`).
