# Warehouse

Сервис владельца для ведения всех его проектов. Сейчас строится первая подсистема —
**диспетчерская**: закрытая страница и бот Telegram, которые показывают «Ждёт вас», общую очередь
сборок macOS и связь проект ↔ сессии Claude ↔ PR.

- Дорожная карта: [docs/roadmap.md](docs/roadmap.md)
- Спецификация: [docs/superpowers/specs/2026-11-25-dispatch-design.md](docs/superpowers/specs/2026-11-25-dispatch-design.md)
- План: [docs/superpowers/plans/2026-11-25-dispatch.md](docs/superpowers/plans/2026-11-25-dispatch.md)
- Next.js здесь новее, чем в обучающих данных: правила в [AGENTS.md](AGENTS.md), документация в
  `node_modules/next/dist/docs/`.

## Команды

```bash
pnpm install
pnpm test        # vitest, база внутри процесса
pnpm test:pg     # те же тесты через боевой драйвер на настоящем Postgres (TEST_DATABASE_URL)
pnpm test:e2e    # сборка + браузерные тесты
pnpm typecheck
pnpm lint
pnpm build
```

## Правила

- Никаких секретов в репозитории (он публичный): только имена переменных в `.env.example`.
- Сборка и тесты только на `ubuntu-latest`; ни одного задания на macOS.
- Без входа владельца не отдаётся ничего. Открыты только `/login`, `/auth/*` и приёмники
  (`/api/github/webhook`, `/api/report/*`, `/api/telegram/webhook`, `/api/cron/tick`), каждый со
  своей проверкой подписи или токена.
- К базе (Postgres в Neon) ходит только сервер по `DATABASE_URL`. Supabase не используется.
- Схема базы — миграции в коде (`lib/store/migrations.ts`); сервис применяет их сам при тике.
  Вышедшую миграцию не правят, изменения идут новой.
- Тесты хранилища идут на Postgres внутри процесса (PGlite) и, в CI, на настоящем Postgres через
  боевой драйвер: они по-разному кодируют параметры.
- Вход — через то же приложение GitHub: подписанная cookie `wh_session` на 30 дней, проверяется в
  каждом обработчике `/api` рядом с данными; `proxy.ts` только отсекает запросы без cookie.
- Минутного тика нет: `.github/workflows/tick.yml` будит сервис раз в 5 минут. В его лог нельзя
  печатать ответ сервиса — логи публичные.
- Из сессий в базе хранится только разобранное состояние, строка состояния и не более 300
  символов хвоста сообщения.
- Вся логика — чистые функции в `lib/domain/`, покрытые тестами; сначала падающий тест, потом код.
- Тексты интерфейса и сообщений — на русском, идентификаторы в коде — на английском.
- Оценки времени в интерфейсе — со знаком «~»; неизвестное — «~?».

## Строка состояния для Warehouse

Каждое сообщение, после которого ты останавливаешься, заканчивай отдельной последней строкой:

`Статус: <состояние> — <одна строка>`

- `ждёт владельца` — без владельца дальше нельзя: что именно от него нужно (решение, мерж, проверка на устройстве, секрет).
- `работаю` — ты остановился, но вернёшься сам: чего ждёшь (CI, событие PR, таймер). Если следишь за PR и чинишь его — `работаю — слежу за PR #N`.
- `готово` — работа закончена и от владельца ничего не нужно: что сделано.

Строку читает сервис Warehouse и показывает владельцу; без неё сессия попадает в список «без статуса».
